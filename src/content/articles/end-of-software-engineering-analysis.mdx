## 先說結論

《The End of Software Engineering》這篇論文的核心主張只有一句話：**程式碼從「系統本身」降級為「推理的拋棄式工具」，軟體交付從「AI → 軟體 → 結果」縮短為「Agent → 結果」。**

它的價值不在於預測時間表，而在於把這個轉變講成第一性原理：傳統軟體要求人類預先寫死所有決策，複雜度指數成長而人類認知恆定；Agent 把決策推遲到執行期，用完即丟，因此解耦了人類認知的上限。

但同一篇論文也親手給了最強的反證：EvoClaw 連續演化測試中，Agent 成功率從孤立任務的 80% 以上暴跌到最高 38%。所以正確的讀法是：**增強範式今天已可用，全自主軟體工程仍是多年研究問題。**

## 這篇論文真正解決的問題

它解的不是「怎麼用 Copilot 寫更快」，而是「為什麼 Agent 不是效率工具，而是必然的交付革命」。

《The End of Software Engineering》給出的答案鏈有三環：

1. **複雜度必然撞牆。** 傳統軟體 `S=(C,D,E)` 的決策邏輯 `D` 必須在執行前由人類寫完。n 個元件的交互路徑上界是 `Θ(2ⁿ)`，模組化只能降低常數，改不了漸進複雜度。
2. **Agent 換了成本結構。** Agent 系統 `A=(M,T,M,Π)` 的迴圈是 `a_t ← M(s_t, ℳ)`，程式碼只為當次解路徑生成。模型容量 `C_M` 隨算力成長，不再綁死人類認知。
3. **商業史就是複雜度轉移史。** 本地授權 → SaaS → AaaS (Agent-as-a-Service)，每次都是由更能吸收複雜度的一方接手。SaaS 省掉機房，AaaS 省掉「指定做法」，使用者只需指定要什麼結果。

## 流程拆解

這篇論文可以拆成一條可重用的分析流水線：

1. 定義兩種系統：靜態 `S` vs 動態 `A`。
2. 證明舊正規化的複雜度上限。
3. 對照三代交付模型 (Table 1：授權 / 訂閱 / 按結果計費)。
4. 指出過渡方案的結構缺陷 (`AI → 軟體 → 結果` 仍有人類瓶頸)。
5. 提出新學科與新職能 (意圖架構師 / 協調者 / 審計者)。
6. 用 benchmark 校準：報喜與報憂並陳。
7. 給出四階段路線圖 (工具增強 → 單任務自主 → 多 Agent 團隊 → 自演化生態)。

其中第 6 步是整篇最值得保留的方法：先看 SWE-bench 的突破，再看 EvoClaw 的懸崖，避免把範式主張讀成現況描述。

## 關鍵數據：喜與憂要分開看

喜的三筆，皆出自論文 §5.1：

- **SWE-bench Verified**：Lingma SWE-GPT 72B 修復 30.20%，接近 GPT-4o 的 31.80%；7B 版也有 18.20%，證明流程資料訓練可以彌補參數量差距。
- **LangChain 多 Agent 協調**：20+ 企業除錯流程中，根因定位時間省 93%，單月省 200+ 工程小時。關鍵在編排與共享上下文，而非單體變強。
- **Hermes Agent 自演化迴圈**：任務完成後自動生成可重用 Skill，调用中發現不足自動補丁，跨 session 靠 FTS5 + LLM 摘要維持記憶。

憂的一筆，出自論文 §5.2 引用的 EvoClaw (Deng et al., arXiv:2603.13428)：

![EvoClaw 性能懸崖：孤立任務 82%  vs 連續演化 38%。](/article.ai/articles/end-of-software-engineering/figure-02-evoclaw-cliff.svg)

EvoClaw 點出的四個失敗模式值得逐字記下：上下文漂移、錯誤級聯、無技術債意識、驗證保真度不足。Agent 能通過測試，卻能在新輸入下藏語義錯誤。

## 主張分級：哪些可信，哪些還不行

**原文明說**：`S` 與 `A` 的形式定義、三代劃分、LangChain 對 Agentic Engineering 的定義 (2026-04)、四階段路線圖、上述四筆數據。

**可直接推出**：AI 輔助寫碼無法突破複雜度上限，因為交付物仍是靜態 `D`；人類職能必須從 code author 轉為意圖、協調、審計，否則發揮不了 Agent 槓桿。

**合理推斷**：`Θ(2ⁿ)` 是教學式簡化，實務依賴稀疏不會全連接，但方向成立；Hermes 的 create-use-patch 迴圈是 Stage II → III 的最小可行橋樑，比空談 swarm 更值得先複刻。

**未被支撐**：模型容量隨算力指數成長不代表任務成功率同速成長，論文沒給轉換函數；Hermes 超過 179,000 GitHub stars 的數量級異常，未給統計口徑，不可引用；Stage IV 在 2028 年後、四階段年份、按結果計費將取代訂閱制，皆屬預測而非推論。

## 哪些步驟適合做成 skill 或自動化

這篇論文其實藏了一條 skill 流水線：意圖 → 計畫 → 執行 → 審計 → 技能沉澱。

可以自動化的有四段：

1. 意圖規格化檢查：目標、約束、驗收標準缺一不可，缺了就拒絕執行。
2. 多 Agent 編排：分派、共享記憶、交叉驗證，這正是 LangChain pilot 證明有效的地方。
3. 成果審計：超越正確性，補 robustness 與可維護性評分。
4. 技能沉澱：Hermes 式 Skill 生成與自補丁。

不適合全自動的也有三段：長上下文狀態壓縮、技術債感知、倫理治理。論文自己承認這些仍需人類在迴圈內。

如果要做成 repo-local skill，我會定位成 `agentic-outcome-loop`：觸發詞是 `intent → plan → exec → audit → skillify`；它負責執行與沉澱，而本文所用的文獻判讀工作仍由分析型 skill 負責，兩者以驗收標準與審計日誌為介面。

## 風險與盲點

1. 單一業界作者的觀點型預印本，benchmark 皆為二手引用，無復現細節。
2. 形式化不嚴謹：`a_t ← M(s_t)` 迴圈沒有收斂、終止與成本界。
3. 成本與安全缺席：Token、延遲、幻覺、權限外溢、失敗風險由誰承擔，全未量化。
4. 不要把工具名當方法：Devin、OpenHands、Copilot 在原文多為列舉背書，非受控比較。

## 我們的判讀

《The End of Software Engineering》最值得保留的不是「軟體工程已死」的標題，而是一個可檢驗的切割：**交付物是靜態程式碼，還是交付結果的能力本身。**

用這個切割回頭看，Copilot 是舊範式的加速器，Hermes 與 LangChain orchestration 才是新範式的雛形。而 EvoClaw 的 38% 則是必要的冷水：記憶體架構與驗證框架補上之前，正確姿勢是人類在駕駛座旁監督、Agent 握方向盤，而非完全放手。
