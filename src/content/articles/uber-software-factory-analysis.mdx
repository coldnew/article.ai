## 先說結論

Uber 工程部落格《Running a Software Factory Efficiently at Uber Scale》（作者 Distinguished Engineer Uday Kiran Medisetty，2026-08-27 發布，經 @UberEng 分享，約 220 萬瀏覽）給出了大企業 AI 編碼帳單的第一份完整交代：**超過 70% 的 PR 由 agent 產出、3,600 個 skill、每天 3 萬次執行**，而 2 月到 8 月請求量漲 9.4 倍的同時，總支出自 4 月起大致持平。做法不是砍模型、不是等降價，而是把總支出拆成**六項相乘的成本等式**，專打中間三項「agent 自己加的戲」。

這篇是前篇 OpenAI 內部工具文的完美對照：OpenAI 回答「工具從哪長出來」，Uber 回答「長出來之後怎麼不讓它吃垮你」。

## 這篇文章真正解決的問題

它回答的是規模化後的帳單問題：**在不犧牲產出品質的前提下，讓單位成本下降追上用量成長**。關鍵方法論誠實之處（原文明說）：把同一模型固定住再量（2026 年 2–7 月），排除模型升級帶來的干擾，證明降幅是自己的優化掙來的，不是 vendor 降價送的。

## 流程拆解

### 四層架構：越專用，越可控

Uber 把 agent 用量分成由專到廣的四層，越往專用層，對成本、品質、模型選擇的掌控力越高。核心戰略轉移（原文結論原話改寫）：**從互動式工作流轉向 fully managed agent**——優化一支有 benchmark 的專用 agent 艦隊，比優化幾千名工程師各自的終端 session 更划算。越來越多 session 甚至不是人類發起的：code review、自癒 CI、E2E PR、on-call 分診、debug 都是 managed agent 主動開工，人類只做審查與升級處理。

### 六組優化槓桿

1. **模型選擇是 benchmark 問題，不是偏好問題**——固定四步：拿該 agent 的真實工作建 benchmark → 同一 harness 可換任何模型 → 搬到 Pareto 最優者 → 持續搬（前沿幾週就變）。實例 uReview（全 PR 的 AI review）：用真實 bug 分難易建 benchmark，以 F1＋單次成本選型，F1 上升同時成本大降。另有內部 Uber SWE Benchmark，橫跨 frontier 與 open-weight 模型。
2. **影響最大的單一槓桿：subagent 預設模型**——主模型做拆解與驗收，執行細節的子任務預設丟給較弱便宜的模型（可手動覆寫）。隨著多 agent 編排比例上升，這個預設值越來越值錢。
3. **預設值開刀**：400K token 自動 compaction（即使是 1M 上下文模型）；reasoning effort 預設 Medium（輸出 token 單價數倍於輸入）；prompt cache TTL 按經濟學調——讀取 0.1 倍價、寫入加價，互動式 session 因工程師常閒置超 5 分鐘改用 1 小時 TTL，短命 subagent 維持 5 分鐘。
4. **MCP schema 稅**：100+ 工具預載給每個 session 帶來約 50K–70K token 開銷且每 turn 重送。解法是 1,000+ MCP server 經統一 gateway，以 **CLI 呼叫時動態解析＋tool search 按需載入**，schema 不再進上下文；SaaS 廠商的臃腫 server（單家 34–49 個工具、約 22K token）同樣收編。
5. **Code-mode**：把「一次 SQL＝提交＋輪詢＋取結果」的 N 個 model turn 收斂成 subprocess 裡的一段 Python，只回傳摘要。實測省 55%–約 100%，批次工作流省 90% 以上；25+ 預建 skill 讓最便宜路徑成為預設路徑。
6. **Graph 接地＋可見性**：AI Context Graph（2,400 萬節點、8,000 萬邊，整合 30+ 內部系統）；同題實測有接地 38 秒答對、無接地 20 分鐘答錯。status line 即時花費計數器、共用 spend tier＋Slack 推播、掃 16 種反模式的 session dashboard（原文截圖示例可省約三成）把浪费變成每個人看得見的數字。

## 哪些步驟適合做成 skill 或自動化

- **Benchmark-driven 選型迴圈**：固定四步，可直接做成 repo-local skill——從生產 log 抽真實任務建成效集，輸出 Pareto 表， frontier 一動就重跑。
- **Subagent 降級預設**：任何多 agent 編排的預設配置項，零成本照抄。
- **Code-mode 封裝**：把 chatty 工具協議（輪詢、翻頁、重試）包成一次執行的腳本＋只回摘要，做成 skill 模板。
- **16 反模式掃描器**：session 結束後掃 trace（大 MCP 回應常駐、cache 過期續跑、Opus 殺雞用牛刀），輸出金額＋修法——個人版可用輕量規則先行。
- **不適合照抄**：千級 MCP gateway 與 2,400 萬節點 Context Graph 是平台團隊規模的產物；小團隊的對應物是「常用表與服務的精簡可查詢索引」，而不是自建 graph。

## 風險與盲點

- **歸因口徑黑箱（未被支撐）**：「70% PR attributed to agents」從未說明定義——碰過 agent 的 PR 都算，還是 agent 為主要作者才算？分母是否含 bot 自動 PR？這是全文最大的方法論缺口。
- **只給比率，不給絕對金額（未被支撐）**：7 倍用量、−52% 單位成本，總支出「大致持平」——若基數極大，持平本身仍是巨額；且 session 成本數據自 5 月底才有，卻談「6 月高峰」，基期很短。
- **品質證據單薄（原文明說＋推斷）**：「維持或提升品質」只有 uReview 的 F1 一個公開實例，其餘品質訊號（revert rate、MTTR）只出現在「我們會追蹤」的表格裡，沒有數字。
- **作者自陳的但書值得尊重（原文明說）**：具體降幅取決於 codebase、團隊規模與工作流，可遷移的是方法論——小團隊照抄數字會失望。
- **原文疑似筆誤**："24M nodes and 80M edges across 86 nodes and 117 edge types"——86 應為節點「型別」之誤，本文逕寫為 86 種節點型別。
- **社群回應是背書，不是驗證**：Roblox 的 Chase 回覆「會偷走一堆點子」、Gaetan Semet 稱「Uber 順手解決了 agentic coding 的所有問題」——熱烈，但無人獨立驗證數字。
