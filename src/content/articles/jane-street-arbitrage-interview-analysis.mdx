## 第一輪：對象建模只是入場券

【原文明說】題目給定的七個對象——Instrument、Exchange、Quote/OrderBook、Market Data Listener、Order Book Manager、Arbitrage Engine、Execution Router——構成一條單向鏈路：Market Data → Order Book → Arbitrage Engine → Execution Router。Listener 的關鍵優化已經寫在題目裡：收到某個 Instrument 的行情，只重算**這一個** Instrument 的全交易所最高 Bid 與最低 Ask，而不是掃全市場。

【原文明說】套利觸發條件只有一行：`max(Bid) > min(Ask)`。但小路強調，這行只是起點，後面四個細節才是面試官要聽的：size 取 `min(bid_size, ask_size)`、價差覆蓋手續費與滑點、加安全閾值 margin、準備一兩個介面簽名（例如 `OrderBookManager.getBestBidAsk(InstrumentId)` 返回 O(1)）。

## 真正的陷阱：legging risk

【原文明說＋合理推斷】多數人看到 `max(Bid) > min(Ask)` 就下單，漏掉的是兩條腿的 Order **不是原子提交**：A 賣單與 B 買單之間隔著網路延遲，第二條腿抵達交易所時，價差很可能已經收窄甚至消失。這是整道題真正的陷阱，也是面試官反覆追問的方向——換句話說，**這題考的不是會不會發現價差，而是知不知道發現價差之後風險才開始**。

【原文明說】對策有三件套：判斷邏輯加安全閾值 margin（套利空間必須大於某個值，覆蓋延遲和滑點）；partial fill 之後想清楚另一條腿怎麼辦（hedge 還是 cancel）；size 與費用如上節。

## Follow-up：100 萬 updates/sec 要講到什麼顆粒度

【原文明說】方向是對的——把計算範圍從「全市場」縮小到「發生變化的 Instrument」。但「減少全域鎖競爭」「避免不必要的記憶體分配」這種回答太泛，面試官想聽的是具體機制，小路直接開了名詞清單：

1. **按 instrument_id 做 sharding**：一致性雜湊把同一 instrument 的所有更新路由到固定執行緒/core——天然無鎖，且 cache locality 好。
2. **Best Bid/Ask 用定長陣列**：按 exchange_id 索引，更新 O(1)。
3. **JVM 系避 GC pause**：off-heap / primitive array，或用 **LMAX Disruptor** 這種 ring buffer 把 ingestion 和計算解耦。
4. **stale quote 處理**：Quote 加 TTL，交易所連接斷了不能拿舊報價繼續判斷。
5. **防重複下單狀態機**：pending / triggered / filled。

![100 萬 updates/sec：範圍縮小＋每個 shard 內的具體機制。](/article.ai/articles/jane-street-arbitrage-interview/figure-02-scale.svg)

<small class="figure-caption">圖 2｜本站依貼文重繪：一致性雜湊分流到固定執行緒後，每個 shard 內的五個具體機制；底線是小路的判準——泛泛而談沒有分量。</small>

【合理推斷】這五條其實是同一句話的五種說法：**延遲的敵人是共享可變狀態與不可預測的停頓**，sharding 消滅共享、定長陣列消滅分配、Disruptor 消滅鎖、TTL 消滅髒讀、狀態機消滅重送。能講出這一層，追問就結束了。
